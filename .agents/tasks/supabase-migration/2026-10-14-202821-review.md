# Supabase Migration for Python with Nawar

The platform has been migrated from Prisma/PostgreSQL to Supabase, establishing dual client configuration (anon key for RLS-bound operations, service role for admin bypass), implementing Supabase Auth for user management, and creating a comprehensive RLS policy schema. Video gating via `ProtectedVideo` component correctly gates content behind Supabase-based authentication. Arabic comments and UI messages are preserved throughout.

## High-level view

The Supabase client configuration creates two clients: `supabase` with the anon key (respects RLS) and `supabaseAdmin` with the service role key (bypasses RLS). The backend exclusively uses `supabaseAdmin` for all database operations, which means RLS policies only protect direct Supabase access, not API-mediated access. This is an intentional pattern for server-side operations, but the service key must be protected.

Authentication flows through Supabase Auth on both frontend and backend. The frontend `AuthContext` subscribes to `onAuthStateChange` and extracts user metadata from sessions. The backend `auth.js` middleware calls `supabase.auth.getUser(token)` to validate JWT tokens, then fetches the user profile from the `users` table using the admin client to bypass RLS.

The schema.sql defines comprehensive RLS policies: users can only read/write their own progress and watch history; anyone authenticated can read comments; lessons are publicly readable when published; admin users (via the `is_admin()` function) can access everything. The `handle_new_user()` trigger auto-creates user profiles on Supabase Auth signup.

The frontend api.js service properly extracts the Supabase session token via `getAuthToken()` and attaches it as a Bearer token to all backend requests. The REST API structure is unchanged — the same endpoints exist with the same contracts.

The orphaned Prisma directory contains a schema and seed file that import `@prisma/client`. These are dead code from the previous implementation and should be deleted to avoid confusion. The Supabase seed script at `backend/supabase/seed.js` correctly replaces the Prisma seed logic.

## Supabase client dual-mode configuration

All controllers use `supabaseAdmin` for database operations, which bypasses RLS. Authorization is enforced at the API layer via `protect` and `adminOnly` middleware. This means the service key is the single point of trust — if compromised, RLS offers no protection.

## RLS policy coverage

The schema.sql defines policies for all tables:

- `users`: read own / admin read all / update own / insert own
- `lessons`: read published / admin full access
- `lesson_progress`: user owns their records
- `watch_history`: user owns their records
- `comments`: authenticated read all / user manages own
- `site_visits`: insert all / admin read

The `is_admin()` helper uses `SECURITY DEFINER` to safely query the user's role. The auto-profile trigger `handle_new_user()` extracts name from `raw_user_meta_data`.
